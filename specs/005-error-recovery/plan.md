# Implementation Plan: Error Recovery System

**Branch**: `005-error-recovery` | **Date**: 2026-03-16 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/005-error-recovery/spec.md`

## Summary

Implement a comprehensive error recovery system that provides automatic retry with exponential backoff, circuit breaker pattern for failing services, graceful degradation for non-critical components, and intelligent auto-restart for crashed services. The system will centralize error recovery logic (currently scattered across components), add circuit breaker protection for external APIs, implement service health classification, and provide intelligent restart with backoff. All recovery actions will be logged to the audit trail and state will be persisted to survive system restarts.

**Technical Approach**: Create a centralized `ErrorRecovery` module with `RetryPolicy`, `CircuitBreaker`, and `ServiceHealthManager` classes. Integrate with existing `AuditLogger` for logging and extend `health_check.py` for monitoring. Persist recovery state in `AI_Employee_Vault/.state/recovery_state.json`. Replace scattered retry logic in watchers with centralized implementation.

## Phase 0: Research & Design Decisions

### Research Topics

1. **Retry Patterns**
   - Exponential backoff algorithms
   - Jitter strategies to prevent thundering herd
   - Retry budget patterns
   - Idempotent operation design

2. **Circuit Breaker Patterns**
   - State machine design (closed/open/half-open)
   - Failure threshold strategies
   - Cooldown period calculation
   - Half-open testing strategies

3. **Service Health Management**
   - Service classification (critical vs non-critical)
   - Degradation detection algorithms
   - Health check integration patterns
   - Recovery detection strategies

4. **State Persistence**
   - Atomic file write patterns
   - JSON schema versioning
   - Corruption recovery strategies
   - State migration patterns

### Key Design Decisions

**Decision 1: Centralized vs Distributed Error Recovery**
- **Chosen**: Centralized module (`scripts/error_recovery/`)
- **Rationale**: Eliminates code duplication, ensures consistent behavior, easier to test and maintain
- **Alternatives Considered**:
  - Keep scattered implementations: Rejected due to inconsistency and maintenance burden
  - Separate service: Rejected due to added complexity and latency

**Decision 2: Decorator vs Explicit API**
- **Chosen**: Both - decorators for convenience, explicit API for complex cases
- **Rationale**: Decorators provide clean integration for simple cases, explicit API allows fine-grained control
- **Alternatives Considered**:
  - Decorators only: Rejected due to limited flexibility
  - Explicit API only: Rejected due to verbose integration code

**Decision 3: Circuit Breaker Scope**
- **Chosen**: Per-service circuit breakers (gmail_api, whatsapp_web, linkedin_api)
- **Rationale**: Isolates failures to specific services, prevents cascading failures
- **Alternatives Considered**:
  - Global circuit breaker: Rejected due to lack of isolation
  - Per-operation circuit breakers: Rejected due to excessive complexity

**Decision 4: State Persistence Strategy**
- **Chosen**: Single JSON file with atomic writes
- **Rationale**: Simple, follows existing patterns, sufficient for scale
- **Alternatives Considered**:
  - SQLite database: Rejected due to added dependency and complexity
  - Multiple JSON files: Rejected due to consistency challenges

## Phase 1: Data Model & Contracts

### Core Entities

**RetryPolicy**
- Configuration for retry behavior
- Fields: base_delay, max_attempts, max_delay, backoff_multiplier, jitter_enabled
- Methods: calculate_delay(attempt), should_retry(attempt, error)

**CircuitBreaker**
- State machine for failure protection
- States: CLOSED (normal), OPEN (failing), HALF_OPEN (testing)
- Fields: service_name, state, failure_count, last_failure_time, cooldown_period, failure_threshold
- Methods: call(operation), record_success(), record_failure(), transition_state()

**ServiceHealth**
- Health status tracking per service
- Fields: service_name, state (healthy/degraded/failed), last_check_time, consecutive_failures, restart_count, last_restart_time
- Methods: mark_healthy(), mark_degraded(), mark_failed(), should_restart()

**RecoveryState**
- Persistent state container
- Fields: circuit_breakers (dict), service_health (dict), retry_counters (dict), last_updated
- Methods: save(), load(), get_circuit_breaker(service), get_service_health(service)

def check_circuit_breakers() -> Dict:
    """Check circuit breaker states"""
    recovery_state = RecoveryState.load()
    open_circuits = [
        name for name, cb in recovery_state.circuit_breakers.items()
        if cb.state == "OPEN"
    ]
    return {
        "status": "warning" if open_circuits else "healthy",
        "open_circuits": open_circuits,
        "total_circuits": len(recovery_state.circuit_breakers)
    }

## Architecture Decision Records (ADRs)

The following architectural decisions should be documented as ADRs:

1. **ADR-001: Centralized Error Recovery Module**
   - Decision: Create `scripts/error_recovery/` module for all recovery logic
   - Context: Retry logic currently scattered across watchers
   - Consequences: Single source of truth, easier testing, consistent behavior

2. **ADR-002: Circuit Breaker Per-Service Scope**
   - Decision: One circuit breaker per external service (gmail_api, whatsapp_web, linkedin_api)
   - Context: Need to isolate failures without excessive complexity
   - Consequences: Good isolation, manageable state size, clear failure boundaries

3. **ADR-003: File-Based State Persistence**
   - Decision: Single JSON file for all recovery state
   - Context: Must survive system restarts, follow existing patterns
   - Consequences: Simple, consistent with vault architecture, sufficient for scale

## Risk Analysis

### Technical Risks

1. **Risk**: State file corruption during system crash
   - **Mitigation**: Atomic writes with temp file + rename, backup on corruption
   - **Likelihood**: Low
   - **Impact**: Medium

2. **Risk**: Circuit breaker false positives (opening on transient issues)
   - **Mitigation**: Configurable thresholds, retry before circuit breaker
   - **Likelihood**: Medium
   - **Impact**: Low

3. **Risk**: Performance overhead from state persistence
   - **Mitigation**: Async writes, batch updates, in-memory cache
   - **Likelihood**: Low
   - **Impact**: Low

### Operational Risks

1. **Risk**: Migration breaks existing watcher functionality
   - **Mitigation**: Comprehensive integration tests, gradual rollout, rollback plan
   - **Likelihood**: Low
   - **Impact**: High

2. **Risk**: Alert flooding when multiple services fail
   - **Mitigation**: Rate limiting on alert creation (max 1 per service per 5 minutes)
   - **Likelihood**: Medium
   - **Impact**: Medium
